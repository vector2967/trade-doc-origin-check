# 체험하기 기획 (계정 없이 써 보기)

> 상태: 기획 초안 (2026-11-10). D1 = 실제 실행으로 확정. 프론트·백엔드 세션이 이 문서를 보고 나눠서 만든다.

## 1. 목표

- 가입하지 않은 방문자도 **버튼 한 번**으로 서비스에 들어와, 서류를 끌어다 놓고 결과 화면까지 끝까지 본다.
- 방문자는 서류를 갖고 있지 않으므로, 화면 위에 **파일 탐색기처럼 생긴 창**을 띄우고 그 안의 체험용 서류를 **여러 개 한꺼번에 끌어다 놓게** 한다.
- 실제 업로드 흐름(새 점검 창 → 접수 → 처리 중 → 결과)을 그대로 거치게 해서, 체험이 곧 실제 사용법 학습이 되게 한다.

### 하지 않는 것 (1차)
- 체험 사용자가 **자기 PDF**를 올리는 것 → 막는다(비용·악용·개인정보).
- 체험 계정을 정식 계정으로 바꾸는 것 → 가입은 따로 한다(체험 데이터는 옮기지 않음).

## 3. 체험용 서류 세트

과제 데이터셋(set01~13, 정답지 A~M)에서 **우리 판정이 정답과 같은 세트**만 고른다. 폴더 이름은 실무자가 보는 말로 붙이고, 결과(판정)는 이름에 드러내지 않는다.

| 폴더 이름(탐색기에 보이는 이름) | 원본 | 파일 | 정답 판정 | 보여 줄 장면 |
|---|---|---|---|---|
| 말레이시아 · 냉동 고등어 | set04 | 6개 | 보완 요청 (C/O 송장번호 ≠ 인보이스) | 불일치 하이라이트, 보완 요청 메일 |
| 태국 · LED 모니터 외 1건 | set03 | 6개 | 검토 필요 (HS 10단위 끝자리 차이) | 품목 2개 비교 표, '6단위 같음' |
| 베트남 · LED 모니터 | set11 | 6개 | 미적용 (확인서 결정기준 미충족 N) | 미적용 안내 문서 |
| 독일 · LED 전구 | set02 | 5개 | 특혜 적용 (한-EU 원산지신고 문안) | 문제없는 건은 이렇게 보인다 |

- 파일당 200~300KB, 세트당 약 1.3~1.4MB → 4세트 합쳐 6MB 안쪽.
- 파일 이름은 원본(`01_인보이스.pdf` …)을 그대로 쓴다. 이름으로 서류 종류를 짐작하는 기존 기능(`hintFromName`)이 그대로 동작한다.

## 4. 사용자 흐름

```
랜딩 [체험하기] ──▶ POST /auth/demo (토큰 발급) ──▶ /checks
                                                     │
                     ┌───────────────────────────────┘
                     ▼
   심사목록(빈 상태) + 위쪽 '체험 모드' 띠 + 오른쪽에 [체험용 서류] 탐색기 창이 열려 있음
                     │  폴더 고르기 → 파일 여러 개 선택(전체 선택) → 목록 화면으로 끌어다 놓기
                     ▼
   기존 '새 점검' 창이 파일 6개가 담긴 채 열림 (서류 종류 자동 지정) → [점검 시작]
                     ▼
   처리 중 화면(단계 표시) 약 1~2분 → 결과 상세 (판정 카드·판정 근거·품목 비교·원본 PDF 하이라이트)
                     ▼
   띠의 [가입하고 내 서류로 점검하기] → 가입 창
```

## 5. 백엔드

### 5.1 체험 사용자

`users` 테이블에 열 2개를 더한다(Flyway).

| 열 | 타입 | 설명 |
|---|---|---|
| `demo` | boolean, 기본 false | 체험 사용자 |
| `expires_at` | datetime(6) null | 체험 데이터 삭제 시각(만든 뒤 24시간) |

- 이메일은 `demo-{uuid}@demo.invalid`, 비밀번호 해시는 로그인할 수 없는 임의 값. 이름 "체험 사용자", 회사 null.
- 가입 허용 도메인(`SIGNUP_ALLOWED_EMAILS`)과 무관하게 만든다(가입 API 를 거치지 않음).

### 5.2 API

| Method | Path | 인증 | 설명 |
|---|---|---|---|
| `POST` | `/api/v1/auth/demo` | - | 체험 사용자를 만들고 토큰을 준다. 응답은 로그인과 같은 `TokenResponse`. 토큰 만료 2시간 |
| `GET` | `/api/v1/demo/samples` | - | 체험용 서류 목록(아래 형식) |
| `GET` | `/api/v1/demo/samples/{setId}/{fileName}` | - | 체험용 PDF 원본. `Cache-Control: public, max-age=86400` |

- `GET /auth/me` 응답에 `demo: boolean` 을 더한다(정식 사용자는 false). 체험 사용자의 `expires_at` 은 토큰 만료 시각.
- JWT 에 `demo: true` 클레임을 넣는다.

`GET /api/v1/demo/samples` 응답 예:

```json
{
  "sets": [
    {
      "id": "kl-mackerel",
      "name": "말레이시아 · 냉동 고등어",
      "files": [
        { "name": "01_인보이스.pdf", "size": 231044, "hint_type": "인보이스" },
        { "name": "02_패킹리스트.pdf", "size": 198311, "hint_type": "패킹리스트" }
      ]
    }
  ]
}
```

### 5.3 체험 사용자의 점검 접수 (`POST /api/v1/origin-checks`)

- 기존 API 를 그대로 쓴다(프론트는 같은 함수로 올린다).
- 체험 사용자면 올라온 파일마다 **SHA-256** 을 체험용 서류 목록과 비교한다.
  - 모든 파일이 **한 세트 안의 파일**이면 접수한다(일부만 와도 됨, D3).
  - 체험용이 아닌 파일이 하나라도 있거나 두 세트가 섞이면 → `403 DEMO_SAMPLES_ONLY`.
  - 자기 PDF 를 올려 Upstage 를 쓰는 걸 막는 장치이므로 **프론트 검사와 별개로 반드시 서버에서** 한다.
- 접수 뒤에는 정식 건과 **똑같이 기존 워커가 Upstage 로 보낸다**(별도 agent 없음).
- 사용량 상한(D5): 체험 사용자당 3건 → `429 DEMO_LIMIT`, 서비스 전체 하루 50건 → `429 DEMO_DAILY_LIMIT`. 실패한 건도 1건으로 센다(다시 실행은 세지 않음).
- 다시 실행·삭제·완료 처리는 정식 사용자와 같다.

### 5.4 실제 실행 시 관리할 것

- **대기열**: 체험 건이 몰려도 정식 사용자 건이 밀리지 않게, 워커가 한 번에 제출하는 체험 건 수를 따로 묶는다(예: 동시에 2건). 대기 중이면 처리 중 화면에 "체험 대기열 n번째"를 보여 줄 수 있게 상세 응답에 `queue_position`(체험 건만)을 더한다.
- **결과 흔들림**: LLM 이라 같은 서류도 판정이 가끔 달라진다. 세트 4개는 운영 설정으로 **3번씩 돌려 3번 모두 정답과 같은 세트**만 쓴다(§3 은 후보). 바뀌면 세트를 교체한다.
- **실패**: Upstage 오류로 `failed` 가 되면 기존처럼 [다시 실행]. 체험 띠에 "체험 서버가 붐벼요" 같은 문구는 프론트가 처리한다.
- **서류 묶음 파일**: 원본 PDF 는 정식 건처럼 저장해서 `GET /{id}/file` 과 하이라이트가 그대로 동작한다.
- PDF 원본은 `backend/src/main/resources/demo/{setId}/` 에 두고 `manifest.json`(이름·hint_type·sha256)으로 목록과 해시 검사를 같이 한다.

### 5.5 정리·남용 방지

- 1시간마다: `expires_at` 이 지난 체험 사용자와 그 점검 건·원본 파일·agent 파일을 지운다.
- 하루 상한(D5)은 KST 자정에 초기화한다. 상한에 닿으면 `POST /auth/demo` 는 그대로 두고(둘러보기는 가능), 접수만 막는다.
- `POST /auth/demo` 는 IP 당 시간당 10번. 넘으면 `429 DEMO_RATE_LIMIT`.
- 환경 변수 `DEMO_ENABLED`(기본 true). false 면 체험 API 3개가 `404`.

### 5.6 오류 코드 추가

| 코드 | HTTP | 메시지 |
|---|---|---|
| `DEMO_SAMPLES_ONLY` | 403 | 체험에서는 체험용 서류 창의 파일만, 한 폴더 안에서 골라 올릴 수 있어요. |
| `DEMO_LIMIT` | 429 | 체험에서는 점검을 3건까지 할 수 있어요. 가입하면 계속 쓸 수 있어요. |
| `DEMO_DAILY_LIMIT` | 429 | 오늘 체험 점검이 모두 찼어요. 내일 다시 오거나 가입해서 써 주세요. |
| `DEMO_RATE_LIMIT` | 429 | 잠시 뒤에 다시 시도해 주세요. |

### 5.7 테스트

- 체험 토큰 발급 → `me.demo == true`
- 세트 파일 전부·일부 업로드 → 접수되어 워커로 감(테스트는 가짜 agent)
- 다른 PDF·두 세트 섞기 → 403, 4번째 → `DEMO_LIMIT`, 하루 상한 → `DEMO_DAILY_LIMIT`
- 체험 동시 제출 수 제한이 정식 건을 막지 않음
- 만료 정리 작업이 사용자·건·파일을 지움
- 정식 사용자는 지금과 똑같이 동작(회귀)

## 6. 프론트

### 6.1 들어오기

- 랜딩 머리와 히어로에 **[체험하기]** 버튼(가입 없이 바로). 누르면 `POST /auth/demo` → 토큰 저장 → `/checks`.
- `AuthContext` 에 `demo` 를 둔다. 체험 사용자가 로그아웃하면 토큰만 버린다.

### 6.2 체험 모드 띠

- 앱 맨 위 얇은 띠: "체험 모드 · 1시간 52분 남음 · 체험 데이터는 24시간 뒤 지워져요" + **[체험용 서류 열기]** + **[가입하고 내 서류로 점검하기]**.
- 남은 시간이 10분 아래면 주의 색.

### 6.3 체험용 서류 창 (파일 탐색기 느낌)

화면 안에 떠 있는 창(브라우저 새 창이 아님). 처음 들어오면 오른쪽 아래에 열려 있다.

```
┌ 📁 체험용 서류 ─────────────────────── ─  □  × ┐
│ ← →   체험용 서류 › 말레이시아 · 냉동 고등어      │
├──────────────────┬──────────────────────────────┤
│ 📁 말레이시아 ·… │ ☐ 이름              종류   크기 │
│ 📁 태국 · LED …  │ ☑ 📄 01_인보이스.pdf  PDF  226KB │
│ 📁 베트남 · LED… │ ☑ 📄 02_패킹리스트.pdf PDF 194KB │
│ 📁 독일 · LED …  │ ☑ 📄 03_BL.pdf        PDF  210KB │
│                  │ …                                │
├──────────────────┴──────────────────────────────┤
│ 6개 중 6개 선택 · 왼쪽 화면으로 끌어다 놓으세요   [점검 시작] │
└──────────────────────────────────────────────────┘
```

- **창 다루기**: 제목 줄을 잡고 옮기기, 최소화(오른쪽 아래 작은 칩으로), 최대화 없음(□는 크기 원래대로), 닫기(띠의 버튼으로 다시 열기). 위치는 sessionStorage 에 둔다.
- **고르기**: 클릭 = 하나, Shift+클릭 = 범위, Cmd/Ctrl+클릭 = 더하기·빼기, Cmd/Ctrl+A = 전체, 머리의 체크박스 = 전체. 폴더를 열면 **전부 선택된 상태**로 시작한다(체험은 폴더째 올려야 하므로).
- **끌기**:
  - 선택한 파일을 끌면 여러 장이 겹친 모양 + 개수 배지("6개")가 따라온다(`setDragImage`).
  - 왼쪽 폴더를 끌면 그 폴더 파일 전부를 끈다.
  - `dataTransfer` 에 `application/x-origin-demo` 로 `{ setId, files: [이름…] }` 를 싣는다. 진짜 파일은 싣지 않는다(브라우저가 페이지 안 요소로는 File 을 만들 수 없음).
- **놓기**: 기존 화면 전체 놓기 영역(`Layout` 의 drop 처리)이 이 타입을 알아본다.
  - 해당 PDF 들을 `GET /demo/samples/{setId}/{name}` 으로 받아 `File` 로 만든다.
  - 기존 `NewCheckModal` 을 그 파일들이 담긴 채로 연다. 서류 종류는 manifest 의 `hint_type` 으로 채운다.
  - 이후는 실제 사용과 똑같다.
- **끌기 대신 버튼**: [점검 시작] 을 누르면 선택한 파일로 같은 창을 연다. 터치 기기와 키보드 사용자용.
- **좁은 화면(768px 아래)**: 떠 있는 창 대신 아래에서 올라오는 시트. 끌기 없이 버튼만 쓴다.
- **키보드**: 위아래 화살표로 이동, Space 선택, Enter = [점검 시작], Esc = 최소화.
- **폴더 일부만 고르고 시작**(D3): 허용한다. 창 아래에 "원산지확인서를 빼고 올리면 어떻게 될까요?" 같은 힌트를 한 줄 둬서 일부러 빼 보게 유도한다. 두 폴더를 섞어 고르면 막고 안내한다.
- **사용량 안내**: 띠에 "체험 점검 3건 중 1건 사용". 429 가 오면 가입 유도 문구.
- **처리 중 화면**: 1~2분 걸리므로 기다리는 동안 볼 거리를 둔다. 단계 표시 + "이 사이 다른 폴더도 올려 보세요" + 대기열 순번(`queue_position`).

### 6.4 튜토리얼

- 결과 상세의 기존 튜토리얼은 그대로 쓴다.

## 7. 순서

1. 백엔드: 체험 사용자·`/auth/demo`·`me.demo` (프론트가 바로 붙어 볼 수 있게)
2. 백엔드: 샘플 목록·PDF API, 해시 검사·사용량 상한, 체험 동시 제출 제한
   - 세트 4개를 운영 설정으로 3번씩 돌려 판정이 매번 정답과 같은지 확인(바뀌는 세트는 교체)
3. 프론트: 체험하기 버튼·띠 → 탐색기 창 → 끌어 놓기 연결 → 튜토리얼
4. 함께: 운영에 `DEMO_ENABLED=true` 로 배포, 4세트 끝까지 확인
5. 백엔드: 정리 작업·호출 제한 (**배포 전에 반드시** — 실제로 돌리므로 상한 없이 열면 비용이 샌다)

## 8. 확인 기준

- 랜딩에서 [체험하기] → 결과 상세까지 **3분 안**, 가입·입력 없이
- 4세트를 각각 3번 돌려 판정이 매번 §3 표와 같다
- 체험용이 아닌 파일·두 세트 섞기는 백엔드에서 막힌다(프론트를 거치지 않아도)
- 상한(체험 사용자당 3건, 하루 50건)을 넘으면 Upstage 를 부르지 않는다
- 24시간 뒤 체험 데이터가 DB·저장소에 남지 않는다
- 정식 사용자 화면·API 는 그대로
